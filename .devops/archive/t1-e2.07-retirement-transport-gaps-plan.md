## Problem

### F1 - A retired Model Registry row is never pruned, so a pull leaves the satellite gate-failing

`scripts/lib/sync-bindings.ps1` **inserts** a row for a registry key the target lacks and **stamps** the model values, but it never **removes** a row for a key the source has retired (see its header comment: "INSERTING a row for a key the target registry does not carry yet"). Machinery 44 retired the selectable `parcel-fast` orchestrator and added a load-bearing `prune_files` entry (`.devops/sync-manifest.yaml:81-86`) — but that entry retires the **agent file**, not the registry row.

The manifest comment states the intended invariant: *"a satellite that already synced keeps the orphan file while its Model Registry row is gone, so that satellite's own check-parcel-prefix.ps1 fails 'registry key has no agent file' / 'no Model Registry row' and its pull exits 1."* That holds only for a **fresh** satellite, whose registry is derived from the seed (`base-context.template.md`), which no longer lists `parcel-fast`. A satellite that **adopted** the key earlier keeps the row, and the failure runs the other way: the file is pruned but the row survives, so `check-parcel-prefix.ps1` fails `Model Registry key 'parcel-fast' has no agent file` and the pull exits `1`.

**Measured:** GRID-Link adopted `parcel-fast` in machinery 40 and hit exactly this at the 54 → 59 pull. Hand-migrated 2026-09-18 by deleting the row from `.opencode/plans/base-context.md` and the `agent.parcel-fast` block from `opencode.json`, then `scripts\check-parcel-prefix.ps1 -Sync`. This is a **latent break across every satellite that synced 40–43 and has not been hand-migrated** — its next pull cannot succeed.

**Fix (options):** (a) `sync-bindings.ps1` drops target registry rows whose key is absent from the source registry — the source registry is already documented as the single source of truth, so this is a delete pass symmetric with the existing insert pass; or (b) a declarative `prune_registry_keys:` manifest key, matching the "one declarative line per retirement" philosophy of `prune_files` / `prune_dirs`. F3 decides whether the same pass should also prune a stale `opencode.json` entry.

### F2 - A retired file inside a portable skill is not transported as a prune (false DRIFT)

Machinery 59 culled `.devops/skills/wiki-bootstrap/references/qa-14-testing-standards.md` (commit `6fe6e5f` — a deliberate orphan cull; the skill's `references:` claim drops 19 → 18 and `wiki-bootstrap` goes v3 → v4) but did **not** add the path to `prune_files`. A satellite then sees the skill directory hash differ at the **same** version, so `-Check` reports `DRIFT` *"locally customized?"* and the dead seed is never deleted — the operator is invited to preserve a file upstream retired on purpose.

Two mechanisms are missing, and they compound:

- **No prune declaration.** `prune_files` is exactly the key for "a stale file lingering in an already-synced target"; the v59 cull registered the `docs/` directory removal but not this file.
- **No parent-dir mask for skills.** The prune mask strips a declared `prune_files` entry from the target hash map so a retired file reports `PRUNE` instead of a misleading parent-dir `DRIFT` — but it is built **only for `portable_dirs`** (`scripts/sync-architecture.ps1:373-377`); portable skills are compared with no `$ignore` (`:378`). So even after the file is declared, the skill reports `DRIFT` **and** `PRUNE`. This is the first `prune_files` path to sit under a portable **skill** (every prior entry lived under `.devops/agents`, a `portable_dirs` root), which is why the gap surfaces only now; `scripts/lib/sync-prune.ps1:13-19` documents the mask limitation for `prune_dirs` but not for this case.

**Measured:** GRID-Link flagged `wiki-bootstrap` DRIFT at v59; hand-deleted the file 2026-09-18.

**Fix:** add the path to `prune_files` **and** extend the mask to portable skills (build the same `$ignore` list and pass it to the skill `Compare-Item`), so a retired file under a skill reports `PRUNE`, never `DRIFT`.

### F3 - A permission change to an already-authored `opencode.json` entry never propagates

Machinery 41 established that the sync **inserts** a missing `agent.<key>` entry but **never restructures an entry the target already authored** — only its `model` value is stamped (permissions, key order and formatting stay as authored; `scripts/lib/sync-bindings.ps1:184`). Machinery 56 (`T1-E3.04`) then added `"wiki-writer": "allow"` to `parcel-sprint`'s `permission.task` block. The current seed carries it, and **both** the shared prefix (`.opencode/plans/base-context.md` Orchestrator Presets prose) and the `parcel-sprint` agent file document the two-named-target allow-list — but a satellite that authored the entry in v40, with only `"ptp-parcel-fast": "allow"`, never receives the addition.

The result is a **silent divergence between a satellite's runtime permission and its own documented contract**: the base-context prose says the batch host may spawn `wiki-writer`, while `opencode.json` denies it. The prefix gate does not catch it (it validates model bindings, not permissions).

**Measured:** GRID-Link's `parcel-sprint` block lacked `wiki-writer` until hand-patched 2026-09-18.

**Fix / open question:** is non-propagation intended? If yes, an existing satellite needs a way to **learn** of a permission change to an entry it authored — a `machinery-version`-gated notice, or a manifest key naming the structural permission (e.g. `opencode_permission_overrides`). If the locked-preset permission is meant to be **structural** — as the prose claims — it should propagate the way `model` does. F1's registry-prune pass and this decision should be made together, since both concern "which parts of `opencode.json` does the template own?".

### F4 - A skill's prose changed without a version bump makes the DRIFT verdict ambiguous

`.devops/skills/model-routing/SKILL.md` changed its orchestration row from `parcel` / `parcel-fast` to `parcel` / `parcel-sprint` in commit `e9a8051`, but `version` was left at `8` (last bumped in `6a90266`). `-Check` then labels the differing copy `DRIFT — target v8 vs source v8 (locally customized?)` rather than `UPGRADE`. GRID-Link's first v59 `-Check` reported exactly this.

`DRIFT` is the sync's safety net for a genuinely local customization — the one verdict that must not be overwritten blindly. A no-bump content edit makes it fire on **stale machinery** instead, and the only safe resolution is a byte diff. The friction is small per incident, but it erodes the verdict's meaning: an operator who learns "DRIFT is usually just a version-bump miss" will eventually overwrite a real local edit.

**Fix:** state the discipline — a skill's `version` **MUST** bump whenever its `SKILL.md` or any reference changes — in the wrap-up / sync surfaces, and optionally have `validate.yml` fail when a skill body differs from the released machinery version without a bump. Raise `model-routing` to **v9** now to label the v59 text change (trivial, and it makes the existing satellite `UPGRADE` instead of `DRIFT`).

## Constraints

- **Keep the satellite-authored boundary.** `base-context.md` is the satellite's canonical prefix file; the sync rewrites **table rows only** and never prose. A registry-prune pass must honour that — delete rows, leave prose and repo-specific rules untouched. The same boundary governs `opencode.json`: the sync stamps `model` and inserts absent entries, never rewrites an authored block wholesale.
- **`-SelfTest` and the fixture suites must stay green.** The sync engine is split into dot-sourced `scripts/lib/` modules and `-SelfTest` asserts the module mirror and pins the transport behaviours with satellite-shaped fixtures. Both F1's delete pass and F2's mask extension change `-Check` verdicts, so each needs a fixture that asserts the new verdict (`PRUNE`, not `DRIFT`) against a pre-retirement target.
- **A mask extension changes `-Check` output for every skill.** Verify no other skill currently carries a `prune_files`-shadowed stray before flipping the comparison; the mask must strip only declared prune paths.
- **`machinery-version` bump + `version-history.md` row are mandatory** — `validate.yml`'s *Machinery version discipline* step fails otherwise.
- **No satellite-side edit.** Satellites converge on their next pull; F1/F2/F3 exist precisely to make that convergence self-healing. GRID-Link was hand-migrated only because no mechanism existed yet.
- **Ordering:** F1 is a latent break for any satellite that has not hand-migrated, so — like `T1-E2.06` — the fix should land **before the next satellite pull**. F2, F3 and F4 are not pull-blocking. F1 and F3 share the "what does the template own in `opencode.json`?" decision and should be settled in one pass.

## Explicitly out of scope

- **Migrating any live satellite.** GRID-Link is already converged (hand-migrated 2026-09-18); any other satellite does so on its first pull **after** this fix lands. No satellite is to be hand-patched from here.
- **The `check-parcel-prefix.ps1` four-concern split** (`T1-E2.02`) — F1 touches the registry table the prefix check reads, but the check itself is not restructured here.
- **The portable-surface fold review** (`T1-E2.06`) — a separate, already-parked transport defect. This item does not re-open its F1–F5.
- **Repo-specific prose in a satellite's `base-context.md`.** F1 prunes **rows**; it does not reconcile prose, and must not start.
- **A general capability/permission transport framework.** F3 asks only whether the one structural locked-preset permission should propagate, not for a merge engine over `opencode.json`.
