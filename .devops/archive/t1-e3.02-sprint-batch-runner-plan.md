## 1 Phase 1: Expansion & Scoping
**Skill Executed:** `ptp-context-hunter`

**Intent:**
Add a **sprint batch runner** to the parcel machinery: a dedicated primary agent `parcel-sprint` + skill `@sprint-run` that walks the committed sprint queue and executes each eligible plan **one at a time in a fresh context**, by spawning a new subagent `ptp-parcel-fast` (locked `AUTO`+`SINGLE` preset) per plan. Each plan is claimed on the trunk, run Phases 1→9 with Gates A/B auto-cleared (C `N/A`), and left at `PHASE_9` with **Gate D `OPEN`** — deferred, not skipped. When the queue's eligible set is drained, the host emits one consolidated Gate D report so the user tests all changes once.

Design decisions locked interactively before plan instantiation:
- **Batched Gate D** — run all eligible plans to `PHASE_9`, one report, user tests once. (Documented deviation.)
- **Trunk-sequential** — no `git worktree` per plan; all changes land on one tree. (Documented deviation.)
- **Strict SINGLE per plan** — no `MULTI` escalation; stop-the-line on failure.
- **Per-plan subagent** — fresh context per plan; `parcel-sprint` is the task-allowed host.

**Target-Behavior Spec (WHAT the system must do — no implementation detail; authored via `@wiki-writer` discipline):**

- **S1 — Batch host exists and is selectable, and its consent is informed.** A dedicated primary agent walks the ACTIVE sprint queue and runs each eligible plan through the parcel pipeline **one at a time, in a fresh context per plan**, by delegating that single plan to a dedicated subagent locked to `AUTO` + `SINGLE`. The host is not a single-plan orchestrator; it governs the spawned per-plan runs. Before it claims anything, the host presents an **informed run preview** (eligible plans, skips with reasons, orphan re-adoptions, and the blast radius) and takes the operator's single yes/no — consent for an unattended trunk-writing run is informed, not blind (S4).
- **S2 — Eligibility is deterministic and machine-checkable, evaluated per claim.** From the ACTIVE sprint queue, a plan is eligible iff: (a) `claim_status: QUEUED`; (b) every code in `depends_on` is present in `.devops/archive/`; and (c) none of its `touches` globs overlaps any `touches` glob of any plan currently in `.devops/plans/` — **including plans already batched to `PHASE_9`**. Overlap is the path-prefix rule stated in Phase 5 § Eligibility Predicate. The predicate is evaluated **immediately before each claim, against the live `.devops/plans/`**, not once across the queue — so clause (c)'s batched-`PHASE_9` protection is live rather than dead text. Before spawning, the runner also runs a **queue-pairwise `touches` check** over the still-`QUEUED` set: two queued plans that overlap each other are ordered deterministically (queue order) and only the first is claimed; the later one is **skipped with its reason recorded** (a claim-time overlap is a recorded skip, never a halt and never a silent drop). Non-eligible plans are skipped with their reason recorded; a skip is not a halt. The preflight **run preview** shows the **forecast** eligible/skip sets to the operator, but the forecast is advisory only: the predicate is still re-evaluated per claim, so execution may differ from the preview and the preview never substitutes for the per-claim check.
- **S3 — Per-plan run contract.** The host claims each plan on the trunk (`git mv` + commit message literal `claim: <code>`), runs its Phases 1→9 under the locked `AUTO`+`SINGLE` preset (Gates A/B auto-cleared, Gate C `N/A`), and terminates it at `PHASE_9` with `claim_status: CLAIMED`, still in `.devops/plans/`, Gate D `OPEN`. The run never archives the plan, never advances past `PHASE_9`, and never flips Gate D.
- **S4 — Stop-the-line + recoverable preflight.** Any hard failure stops the batch immediately: no ACTIVE sprint in `.devops/backlog/SPRINTS.md`; non-empty `git status --porcelain`; red baseline (`check-parcel-prefix.ps1` or `check-utf8-agents.ps1` exit ≠ 0); a Phase 3.5 `Unresolvable:`; `PHASE_8_FAILED`; or a per-plan subagent returning `HALT`. Already-completed plans keep their terminal state; the report records the stop point and cause. **Preflight orphan reconciliation:** a plan that is `CLAIMED` in `.devops/plans/`, is in the ACTIVE sprint's queue set, and has never reached `PHASE_9` is an *orphan* (claimed, then the spawn died) — the runner re-adopts it (resumes the per-plan chain from its recorded `Status`) rather than excluding it forever just because it is no longer `QUEUED`. **Resume after a dirty HALT:** a HALT that leaves `git status --porcelain` non-empty would otherwise brick every later run, so preflight offers a resume path — surface the dirty set, require the user to either commit/stash it or explicitly abandon the orphan's claim back to the queue (`git mv` back + `claim_status: QUEUED`), and only then continue. A dirty tree is never auto-cleaned. **Informed confirmation (preview before the single yes/no):** once preflight passes and the eligible set is computed, the host presents a computed **run preview** before asking its one yes/no: (a) the eligible plans with `code` + `title`; (b) the skip list, each entry with its reason; (c) the orphan re-adoption list, if any (surfaced for confirmation — the heuristic cannot distinguish a dead-batch orphan from a live concurrent claim); and (d) a plain-language blast radius — *N plans → N×2 commits on your trunk (no worktree isolation), source edits, one Gate D at the end.* The preview is labelled a **forecast**: per-claim re-evaluation still governs, so the executed set may differ from the preview, and the operator's approval is recorded in the report.
- **S5 — One consolidated, directed Gate D report.** When the eligible set is drained, the host emits a single report at `.opencode/plans/run-sprint-{n}/sprint_run_report.md`. Each run row carries the plan's **code + title**, terminal Status, touched files, and Phase 9 verification evidence. The report also contains: (a) a **Skipped / deferred** table — every non-run plan with its reason (unmet `depends_on`, `touches` overlap, pre-existing `PHASE_9`, within-batch `depends_on`, claim-time queue-pairwise overlap); (b) a **What to do next** block covering all three exits — approved → run the per-plan `@agent-wrap-up` archive sequence (one per batched plan); a plan that fails the operator's test → retry or `PHASE_5_REVISION`; batch halted → the exact resume instruction (fix the cause, or abandon-claim the orphan back to `QUEUED`, then re-run `@sprint-run`); and (c) on `HALT`, the **partial report is emitted immediately** — completed plans at `PHASE_9`, the stop point, the cause, the resume path — rather than waiting for the queue to drain. The report body is echoed in chat **in full** (the complete body, not a summary) because the report path is gitignored/ephemeral (KC Pitfall) and cannot be linked from tracked docs.
- **S6 — Safety unchanged.** Gate D stays the human's: the batch **defers** it, never skips it. Each plan's own Phase 4 spec, acceptance criteria, and Phase 9 verification still apply per plan; no plan may bypass them because it ran in a batch.

### Eligibility Predicate (`sprint-run` §2 — machine-checkable)
**Evaluated immediately before each claim, against the live `.devops/plans/`** (not once across the queue) — that is what makes clause 3's batched-`PHASE_9` protection live.
A queued plan is **eligible** iff all three hold:
1. it sits in the ACTIVE sprint folder with `claim_status: QUEUED`, **or** it is a preflight-reconciled orphan (a `CLAIMED` plan in the ACTIVE queue that never reached `PHASE_9`, re-adopted from its recorded `Status`);
2. every code in its `depends_on` is present in `.devops/archive/`;
3. **no overlap** between its `touches` and the `touches` of **any** plan file currently in `.devops/plans/` (the template excluded) — including plans already batched to `PHASE_9`. Normalize each entry (forward slashes, lowercase, strip a trailing `/**` or `/*`); entry A overlaps entry B when either normalized stem is a path-prefix of, or equal to, the other.

**Queue-pairwise check (still-`QUEUED` set).** Before the first claim, run the same overlap test across every queued plan's `touches` pair. Two queued plans that overlap each other are ordered by queue order: the first is claimed, the later one is **skipped with its reason recorded**. If the overlap is only discovered at claim time (the earlier plan was claimed after the check), the claim-time outcome is the same — a recorded skip, never a silent drop and never a halt (Rule 4, `plan-lifecycle.md:91`).
**Within-batch `depends_on`:** a queued plan whose dependency is still in-batch (not yet archived) is **skipped, never reordered** — the runner does not topologically sort the queue.
**Pre-existing `PHASE_9`:** a plan already at `PHASE_9` when the batch starts is skipped (already batched), not re-run.
Anything failing 1-3 is **skipped with its reason recorded**; a skip never halts the batch.
- `ponytail:` prefix-overlap heuristic — a mid-path wildcard (e.g. `src/*/db`) is not detected; upgrade path = segment-wise glob intersection.
