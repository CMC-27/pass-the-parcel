# Backlog: T1-E1.05 - OpenCode V2 config drift in `opencode.json`

## Theme-Epic: T1 - Parcel Pipeline Machinery, E1 - Model & Config Integrity

**Discovered:** 2026-09-20, during `T1-E1.04` Phase 3 (while verifying the V2 inheritance contract against the canonical OpenCode V2 docs). **Pre-existing — not introduced by that parcel.** Deliberately left unfixed to keep that parcel's write set bounded.

## Findings

| # | Defect | Evidence | Impact |
|---|---|---|---|
| 1 | `opencode.json` declares `"instructions": ["AGENTS.md"]`, but V2 **accepts the field and does not load its entries** — *"use `AGENTS.md` for instructions."* | OpenCode V2 config docs, `instructions` section; confirmed by the `opencode` skill | Currently **masked**: V2 discovers `AGENTS.md` ambiently, so behaviour is correct by accident. The declared field is dead configuration that reads as load-bearing — a future reader could remove `AGENTS.md` believing the config wires it up |
| 2 | `skills: { "paths": [".devops/skills"] }` is **V1 shape**; V2 native is a flat array (`"skills": [".devops/skills"]`) | Same docs, `skills` section; V2 migration guide (`Skills`) | Currently **functional** — V1 syntax is normalized in memory — but it is one of the shapes the migration guide says to convert, and it is the only V1-shaped key left after `T1-E1.04` removed the `agent.<key>.model` values |

> Both are **cosmetic today and load-bearing tomorrow.** Neither breaks a gate, which is exactly why they survived: nothing asserts the difference between "declared" and "loaded".

## Why it is not urgent

V2 normalizes supported V1 syntax without rewriting the source file, and ambient `AGENTS.md` discovery makes defect 1 behaviourally inert. No satellite is broken.

## What a fix would touch

`opencode.json` + the seed `opencode.template.json` (flip `skills` to the array form, drop or correct `instructions`), then any prose that documents the `agent` block's shape (`HOW-TO.md` § Binding note, `SATELLITE-BOOTSTRAP.md` § 2), and a decision on whether the migration is worth doing at all before V2 makes the V1 path definitively unsupported.

## Open question for Phase 3

Convert to native V2 shape now, or keep the supported V1 form until something forces the move? The answer changes the blast radius from two files to a docs sweep.

## 1 Phase 1: Expansion & Scoping
**Skill Executed:** `ptp-context-hunter` (inline, `SINGLE`)

**Intent:**
Make `opencode.json` — and the seed every satellite authors its own copy from — declare **only what OpenCode V2 actually loads**, so the file stops reading as load-bearing where it is not. Today the config carries two shapes that are cosmetic and inert but *misleading*: `"instructions": ["AGENTS.md"]` (V2 accepts the field but does not load its entries — `AGENTS.md` is discovered ambiently, so behaviour is correct by accident) and `skills: { "paths": [".devops/skills"] }` (the V1 object shape; V2's native shape is a flat array, normalised in memory). Nothing breaks today. What breaks is *comprehension*: a future reader can remove `AGENTS.md` believing this field wires it up, and the seed ships that misreading to every satellite that ever bootstraps from it.

**In Scope (the declared `touches` — 4 files):**
1. `opencode.json` — remove the dead `instructions` entry; flip `skills` to the V2-native flat array.
2. `.devops/templates/opencode.template.json` — the same flip in the seed (and its own `_comment` prose, which currently instructs "keep verbatim" for both).
3. `.devops/templates/SATELLITE-BOOTSTRAP.md` § 2 — the migration prose around the seed (front-matter `version:` bump if edited).
4. `HOW-TO.md` § Binding note — the opencode.json prose.

Honouring the question ("convert now or wait") is this parcel's whole decision; a general V1→V2 audit of the repo is not.
- **Any behaviour change.** No agent, permission, prompt path or `default_agent` changes. The config's *effective* meaning is identical before and after — that is the point.
