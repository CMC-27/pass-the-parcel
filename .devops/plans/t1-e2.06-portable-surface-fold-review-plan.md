## Problem

### F1 - A satellite's locally-authored machinery lesson is destroyed by the next pull

`portable_dirs` includes `.devops/rules`, and the engine copies with `Copy-Item $s\* $t -Recurse -Force` (`scripts/sync-architecture.ps1:902,918`). That is a **merge by name**, so `.devops/rules/process-lessons.md` is replaced wholesale from the template on every pull.

Measured 2026-09-16 by diffing the two registers: the template carries **18** entries, GRID-Link carries **15**, and the satellite has exactly **one** entry the template lacks —

> `[2026-09-16] A register row reading COMPLETE is a claim, not a measurement` — `T21-E6` recorded the Firebase Node 20→22 runtime upgrade COMPLETE; six days later `firebase functions:list` reported `nodejs20` on all five functions, including the JWT bridge every authenticated query depends on. The parcel updated one of two declarations and the other one won at deploy time. *Do instead:* re-measure a deployed state from the live artefact rather than the declaration, and when two declarations exist for one setting, name the single owner instead of updating one and leaving the other to win.

Four template entries would arrive in the same pull. So the exposure is asymmetric and silent: the pull looks like a normal upgrade while it discards the one lesson that satellite actually produced — and that lesson is the rule that caught a month-old falsified COMPLETE row.

**Fix:** add that entry to this repo's register verbatim (it is machinery knowledge, not satellite-specific) and attribute its origin. The satellite then converges on the next pull with nothing lost.

### F3 - One rule is genuinely unfolded, and its home is a planning directive

`[2026-09-13] A contract-coverage AC must name an *exported* seam` (line 26) is the only entry with no home yet. Origin is `T22-E1.02`: an acceptance criterion asserted a contract was *"derived from `BriefEditForm`'s field config"*, but that config is module-local, so the criterion was untestable.

`ptp-high-visionary` Phase 4 directive 3 says only: *"**Define acceptance criteria** as a table: behavior criterion + test target."* It requires a test target and says nothing about that target being **exported**, nor about declaring a hand-maintained snapshot as one that does not guard drift.

The asymmetry is the reason to fold it: `wiki_coverage_check.py` **already** requires an *exported symbol* for source-file coverage, so the concept is mechanically enforced after the fact and absent from the directive that would prevent the defect at authoring time. An AC with a module-local target passes Gate B, then Phase 9 either cannot verify it or substitutes a weaker check — a vacuous criterion, sitting at the gate meant to catch it.

**Fix:** extend directive 3 in `.devops/skills/ptp-high-visionary/SKILL.md` and delete the register entry. This skill is **embedded** in `ptp-high-visionary.subagent.md`, and the prefix check validates EMBED markers against `SKILL.md`, so the edit must be followed by `scripts/check-parcel-prefix.ps1 -Sync` or CI fails hard.

### F4 - `@agent-wrap-up` orders satellites to do something inert

Phase 7b step 2 tells the operator that for each modified file under `.devops/skills/` or `.devops/templates/`, they should *"bump `machinery-version:` once in `.devops/sync-manifest.yaml`"*. In a satellite that instruction cannot take effect: the engine *"stamps the TARGET's own `.devops/sync-manifest.yaml` with the **source** machinery-version"* (`sync-architecture.ps1:38-41`), and the manifest is deliberately not on the portable surface.

GRID-Link followed the instruction faithfully at its Sprint 8 close (52 → 53). This repo is at **47**, so the next pull stamps it back down and the bump was inert. The discipline itself is sound — it is enforced correctly template-side by `validate.yml`'s *Machinery version discipline* step, which fails when `version-history.md` carries no release row for the current `machinery-version`.

**Fix:** rescope Phase 7b step 2 to the template and state that a satellite **inherits** the stamped value and must not bump it. This plan keeps its own rule: the machinery edits below bump **47 → 48** and record the literal in `version-history.md`.

### F5 - Pull semantics are undocumented, and misread in both directions

The manifest header and `pull-architecture.ps1` both describe the copy as *"directories copied recursively into the target (overwrite)"*. The engine's real behaviour is narrower than "mirror" and broader than "additive" — `Copy-Item $s\* $t -Recurse -Force` is a **merge by name**:

- A file present in **both** repos is **replaced wholesale** — target-side edits are lost. This is F1's mechanism.
- A file present in the **target only** survives untouched — a satellite-only rule file is never pruned, so "sync" can leave permanent local residue.

A satellite reasoning with either wrong model misjudges what a pull does. "Sync is a mirror" predicts deletions that never happen; "sync is additive" predicts local edits survive when they do not. Neither error is visible in the current wording.

**Fix:** state the semantics in `sync-architecture/SKILL.md` — one paragraph naming the merge-by-name behaviour and both consequences. Optionally mirror one sentence into the manifest header comment, which is the first thing a satellite reads.
