## Findings

| # | Gap | Evidence | Impact |
|---|---|---|---|
| 1 | Every satellite carries the full 34-skill library (GRID-Link: 36, including 2 local additions), but measured parcel-record usage is ~18 skills. | 439-file corpus grep: all `ptp-*`, both orchestrators, `sprint-run`/`plan`/`close`, `agent-wrap-up`, `backlog`, `wiki-writer`, `spaghetti-monster`, `test-and-deploy`, `wiki-lint`, `knowledge-capture` dominate; the rest never appear in the record (conversational skills unmeasurable — audit § Measurement Limits). | The onboarding surface — the audit's identified adoption barrier — is roughly double what a pipeline-carrying satellite needs. |

## Design (membership from measurement, not opinion)

A declared **profile** in the sync manifest — `CORE` (the ~18 measured pipeline skills + guardrail scripts + the agents) vs `FULL` (today's library). Each satellite declares its own tier; the sync respects it (a CORE target must not report the un-installed skills as MISSING/PRUNE). **FULL stays the default** — existing satellites see no behavior change, and CORE→FULL upgrade must be purely additive.

## What a fix would touch

`.devops/sync-manifest.yaml` (the profile declaration + membership list — data, not code), `scripts/lib/sync-manifest.ps1` + `sync-architecture.ps1` (profile-aware comparison), `SATELLITE-BOOTSTRAP.md` (the tier question at bootstrap), `README.md` (the onboarding story), `.devops/skills/sync-architecture/SKILL.md` (the tier switch step).

## Open questions for Phase 3

- [ ] Is the profile a satellite-side manifest key (each satellite self-declares, pull respects) or a template-published pair of sets (or both — template publishes, satellite selects)?
- [ ] How are conversational skills judged (unmeasurable from plans — operator judgement, or CORE-excluded by default with documented opt-in)?
- [ ] Does the measured membership list live in the manifest (transportable data) or a rule doc (governed prose)? One canonical home per the doctrine.
- [ ] Re-validate membership at each major (T1-E2.08) against fresh usage data, or fixed until revised?

## Why LATER

No current breakage — satellites simply carry unused skills. The mechanism needs design (transport contract change), and its membership evidence should be refreshed once more satellites exist beyond GRID-Link (n=1 today, honestly).

## 1 Phase 1: Expansion & Scoping
**Skill Executed:** `ptp-context-hunter` (inline, `SINGLE`)

**Intent:**
A satellite must be able to declare a **tier** and receive only the machinery that tier needs. Today the portable skill surface is derived as *every folder in `.devops/skills` minus `excluded_skills`* (`.devops/sync-manifest.yaml:20-22`), so a satellite that wants less must hand-maintain exclusions against every pull — drift by construction. The GRID-Link field audit measured that **~18 of the 36 skills a satellite carried actually participate in the plan record** (`.devops/audits/grid-link-field-audit-2026-09-24.md:35`, method at `:22`) — the onboarding surface, the audit's identified adoption barrier, is roughly double what a pipeline-carrying satellite needs. This parcel adds a **profile** (tier) to the transport contract: the template publishes the CORE membership as **data**, each satellite declares its own tier, and the sync respects it. **FULL stays the default** — an existing satellite sees no behaviour change at all — and a CORE->FULL upgrade is purely additive.

**In Scope:**
1. `.devops/sync-manifest.yaml` — the tier contract's data home: a `profile:` scalar (this repo's tier, `FULL` by default) plus a `core_skills:` membership list (the 18 measured slugs), and a header comment stating the contract (membership is data; the satellite's lever is `profile`; FULL default; CORE->FULL additive).
2. `scripts/lib/sync-manifest.ps1` — the tier's **single derivation home**: read a repo's declared tier (validating it at the trust boundary), derive the effective portable skill set from the source's `core_skills`/`excluded_skills` and the target's tier, and derive the tiered-out dirs the prune path deletes.
3. `scripts/sync-architecture.ps1` — profile-aware comparison on **both** `-Check` and the sync copy path (the same derived set drives both), the tiered-out prune, the `.DESCRIPTION` contract, and a new `-SelfTest` fixture proving the tier end-to-end.
4. `.devops/templates/SATELLITE-BOOTSTRAP.md` — the tier question at bootstrap, where a satellite declares it (`version: 15 -> 16`).
5. `README.md` — the onboarding story names the tier.

**Out of Scope:**
- **Tiering anything but the skill set.** `portable_dirs` (`.devops/agents`, `.devops/rules`, `.wiki/rules`, `.devops/templates`, `.vscode`) and `portable_files` (scripts, workflows, the plan template) travel **untiered**: all agents and every guardrail script are pipeline, the measured surplus is the skill library, and tiering more surfaces multiplies the derivation for no measured gain. Recorded, not silently done.
- **A satellite-authored membership list.** `core_skills` is template-published data; a satellite's only lever is `profile`. A second per-satellite membership key would be a second dialect of the same rule (`@Managed Simplicity`).
- **`.devops/skills/sync-architecture/SKILL.md` and `.devops/README.md`** — the two doc mirrors that describe the portable-skills derivation (`:39-40`) and the pull workflow. Both sit **outside this plan's declared `touches`**; the changes they need are recorded as follow-up backlog entries in Phase 6 rather than taken here (`.devops/skills/ptp-parcel-fast/SKILL.md` § Plan Settings writer is the byte-stable frozen block; scope discipline is the sprint's own rule).
- **Any live sync against a real satellite.** Behaviour is proved against the `-SelfTest` fixture and throwaway temp trees only (`$env:TEMP\opencode\`).
- **A `machinery-version` bump or a `.devops/logs/version-history.md` row** — Counter Ownership: the follow-up batch wrap-up owns the batch's single increment.
- **`T1-E2.09`** ("satellites are told to bump a counter they do not own") and anything under `.devops/backlog/**` — a parked sibling, explicitly not this plan's scope (sprint.md § Explicitly Out of Scope).

**Perimeter Notes:**
- **The tier is the skill set, and the pipeline survives it.** A CORE satellite keeps every agent (`.devops/agents` is untiered), every guardrail script, and the 18 measured skills — the 7 `ptp-*` personas, `pass-the-parcel`, `sprint-plan`/`sprint-run`/`sprint-close`, `agent-wrap-up`, `backlog`, `knowledge-capture`, `wiki-lint`, `wiki-writer`, `spaghetti-monster`, `test-and-deploy`. Nothing the pipeline *runs* is removed.
- **The measured surplus is a judgement, discharged narrowly.** Skills the corpus grep cannot see (conversational / operator-invoked — `wiki-query`, `model-routing`, `karpathy-guidelines` and the like; `.devops/audits/...:72`) default **out** of CORE and are reachable through the documented, purely additive `profile: FULL` opt-in. No judgement is silently baked into the default.
- **`-SelfTest` fixture count is unchanged.** The fixture plants state in the throwaway target; it adds no manifest entry, so the reported `5 dirs, 34 skills, 19 files` must stay the same (and is asserted as an acceptance criterion).
