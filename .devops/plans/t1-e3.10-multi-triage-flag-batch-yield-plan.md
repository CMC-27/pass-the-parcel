# T1-E3.10 - MULTI-worthy triage flag + batch pause/yield

> **Origin:** The batch presets force `AUTO`+`SINGLE` on every queued plan regardless of complexity, so a `MULTI`-worthy plan can run with no independent reviewer and no adversarial pass. This parcel flags such plans at initiation, lets the operator accept the risk or defer, and adds a pause/yield so a deferred plan is delivered independently by the user. Wave 4 of the batch-hardening sequence.

## 1 Phase 1: Expansion & Scoping
**Skill Executed:** `ptp-context-hunter`
**Intent:**
At batch initiation, flag `MULTI`-worthy plans, let the operator accept the batch risk or defer, and add a pause/yield so a deferred plan is delivered independently by the user before the batch resumes.

**In Scope:**
- `@sprint-plan` records a complexity-triage recommendation per committed plan (the best data is available there, where the plan is read).
- `sprint-run` § 1 preview presents the per-plan fork: **accept batch risk** (`AUTO`+`SINGLE`) or **defer to manual**.
- A `DEFERRED-MANUAL` loop/report state (not a claim status) plus the resume contract: yield → user runs `@pass-the-parcel` `MULTI` to completion → user resumes → the fixpoint re-reads live state.
- `parcel-sprint.agent.md` unique content, `pass-the-parcel` § Batch Runner, `plan-lifecycle.md` § Deviations, and the `base-context` prefix if the yield state is named there.

**Out of Scope:**
- Hard-skipping `MULTI` plans with a recorded reason (rejected — a soft fork with operator choice is the chosen design).
- Auto-classifying complexity mid-run once Phases 1–5 have produced real data.
- Gate D semantics; the consolidated batched verdict remains.

**Perimeter Notes:**
- The pre-run flag is a **guess** — the plan has not been through the phases that would reveal its true complexity. The human decides; the flag only advises.
- The fork must resolve **before** the claim step, or the plan is already `CLAIMED` and no longer claimable by the user's independent run.
- "Accept the risk" must be pre-clearable per plan (and for all), so a fully unattended run stays possible; the pause fires only for plans deliberately deferred.
- Dependency interaction: ship **pure pause** first (stop the line); pause-and-advance is a later refinement.

**Architectural considerations:**
- Pre-run complexity is a **guess**: the plan has not been through Phases 1–5, so the flag advises; the operator decides.

- `@sprint-run`'s premise is unattended execution, so acceptance must be pre-clearable; the pause fires only for plans deliberately deferred.
- Precedent for a user-in-the-loop stop already exists: the preflight dirty-tree resume path.

**Relevant existing decisions:**
