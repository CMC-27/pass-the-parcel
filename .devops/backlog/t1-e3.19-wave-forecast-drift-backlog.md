## Why it is not urgent

No gate is red and no plan is blocked. The forecast is wrong but harmless in the moment — `@sprint-run` never reads the wave numbers, only the `Flag` column, and the eligibility script recomputes the truth on every run. The cost is a misleading sprint record and a planning input that cannot be trusted.

## What a fix would touch

`.devops/skills/sprint-plan/SKILL.md` — § 4b step 3 (the mandate to record a wave decomposition), § 4c step 2 (where the flag is recorded), and the inline template at `:111-120`; `.devops/templates/sprint.template.md` — reconcile against the inline copy (and decide which one is canonical, or make the inline a citation). `@sprint-run` § 1 only if the fork's pointer to the `Flag` column moves. Per-skill version bumps; a `.devops/templates/` change is non-skill machinery, so it carries a `machinery-version` bump.

## Open question for Phase 3

Replace the prediction with the predicate's live output (a recorded *first-pass* eligibility run at commit time, which is what actually happens), or drop the wave column entirely and keep a plain `Flag` table? The first is more honest and still cheap — `scripts/sprint_eligible.py` already emits exactly this — but it makes commit time depend on a script run. The second is smaller and loses the "accepted cost: N verdicts" warning that § 4b step 4 deliberately surfaces to the operator.
