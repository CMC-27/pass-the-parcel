# T1-E4.02 — Review orchestrator/subagent execution topology

## Phase 1 — Intent

Review whether the current parcel execution structure is using subagents correctly or creating unnecessary coordination overhead. The specific suspicion is that the orchestrator owns the final persistence and many subagents are sequential, read-oriented, or prose-returning, which may be adding handoff and reconciliation cost without enough independent execution value.

### In scope
- Audit the real execution topology in the runtime agent config and spawned subagent permissions.
- Compare the documented architecture in the parcel agent prompts against the effective execution flow.
- Decide whether the current topology is still efficient, or whether the repo has drifted into serial orchestration bloat.
- Capture the design recommendation for a simpler or stricter execution model if needed.

### Out of scope
- Rewriting the full parcel system in this parked item.
- Changing project delivery scope or sprint commitments.
- Redesigning unrelated repo governance or wiki rules.

- `.devops/agents/parcel.agent.md` — orchestrator role, delegation map, and gate flow.
- `.devops/agents/parcel-sprint.agent.md` — batch host and locked preset model.

- `.devops/rules/process-lessons.md` — recorded machinery/process lessons about sequencing, drift, and execution patterns.

## Phase 3 — Design questions

- Are the subagents currently acting as independent specialists, or mostly as serial handoff stages?
- Does the orchestrator persist the final state in a way that makes subagent write capability unnecessary for many phases?
- Are any subagents adding clearer isolation than actual throughput gains?
- Is the repo paying a coordination tax without enough parallelism or independent write authority?
- Should review-only subagents remain read-only while execution-heavy phases gain direct write permission?
- Should the current architecture be preserved, simplified, or split into fewer, clearly bounded execution lanes?

## Phase 4 — Candidate approach

1. Audit the lifecycle as actually configured in `opencode.json` and the agent prompts.
2. Measure the cost of serial delegation vs. direct execution in current repo patterns.
3. Determine whether the design is intentionally coordinator-heavy or simply over-structured.
4. Produce a recommendation: retain, simplify, or re-split the topology.
5. Codify the outcome in the repo’s governance or backlog as a follow-up change if warranted.

## Phase 5 — Draft implementation sketch

- Read the live config and compare it to the documented execution model.
- Decide whether the performance issue is a true architectural problem or a repository-specific run pattern.
- If it is a structural issue, reduce the number of serial specialist steps or narrow their responsibilities.
- Capture the decision in a follow-up machinery change or rule update.

## Phase 6 — Risks and edge cases

- The repo may be intentionally structured as a “planner + reviewer + executor” system, even if it is serialized in practice.
- A stricter split may improve determinism but reduce flexibility.
- The same topology may be valid for high-risk work but inefficient for routine local execution.
- The review should distinguish design principle from current runtime cost.

## Phase 7 — Decision gate

This item is a review and design assessment, not an implementation. It should be treated as a structured audit of execution architecture, and it should end in a recommendation rather than a code patch unless the review proves a concrete change is needed.

## Phase 9 — Notes

The review is motivated by a real architectural question raised during the parcel pipeline review: whether the repo is paying a substantial orchestration tax for a multi-agent setup whose phases are effectively serial.

Observed failure mode to include in the review:
- In multi mode, the orchestrator is prompting for a fresh session when it should be spawning the relevant subagents for the next group.
- Concrete symptom: "Next is Group B (spec + plan → Gate B) — fresh session per the one-grouping rule. Say the word."
- This is a contract-level execution bug or policy mismatch if the intended behavior is to keep the orchestrator inside the same parent flow and delegate to subagents instead of restarting the session.
