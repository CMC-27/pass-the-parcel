## 1 Phase 1: Expansion & Scoping
**Skill Executed:** `ptp-context-hunter`

**Intent:**
Make "executed to Gate D, verdict pending" a first-class, machine-checkable plan state so a sprint's intra-queue dependency chains execute correctly — in a batch or in the manual sequential flow — without a per-sprint operator ruling.

The defect: `@sprint-run` § 2 clause 2 requires every `depends_on` code to be present in `.devops/archive/`, but the batch path forbids archiving (every plan stops at `PHASE_9`, `claim_status: CLAIMED`). The only state a batch can produce for a dependency is the state the predicate refuses. Chains therefore execute only their roots. This is codified (not merely missing) in `sprint-run:43,73`, `parcel-sprint.agent.md:145`, and `plan-lifecycle.md:35,72`. Sprint 7's operator ruling ("a batched `PHASE_9` dependency counts as satisfied") overrides the spec at runtime; this parcel bakes the ruling into the state machine.

**In Scope:**

**D1 — New claim status.** Add `GATE_D_USER_APPROVAL` to the canonical claim-status enum and retire the dead `IN_PROGRESS` value (nothing in the repo ever sets it). The enum becomes `QUEUED | CLAIMED | GATE_D_USER_APPROVAL | COMPLETE`, where `CLAIMED` remains the in-flight window (Phases 1→8) and the bottom `Status` stays `PHASE_9` with Gate D `OPEN`. **General, not batch-only:** every path that reaches Phase 9 sets it — the orchestrator/`ptp-code-surgeon` Gate D halt and `ptp-parcel-fast` step 8 — so the manual sequential sprint flow (`plan reaches Gate D → stays in plans → next plan picked up`) works too.

**D2 — Dependency predicate.** A `depends_on` code is **satisfied** when it is either present in `.devops/archive/` **or** present in `.devops/plans/` with `claim_status: GATE_D_USER_APPROVAL`. The disjunction makes the two wrap-up paths compose for free: a manually wrapped plan matches the archive clause; a batched plan matches the status clause. A `GATE_D_USER_APPROVAL` plan that later fails Gate D reverts to `CLAIMED`, so a re-evaluation correctly blocks dependents again.

**D3 — Fixpoint runner.** `@sprint-run` iterates: each pass re-applies the predicate to the remaining `QUEUED` set (queue order) and claims the next eligible plan, until no remaining plan is eligible. Properties to pin: **bounded** (each iteration claims a plan or stops; ≤ N), **deterministic** (queue order), **cycle-safe** (mutual `depends_on` leaves neither eligible → terminate + flag as a queue defect). Preflight gains a **dependency-cycle check** and a **resolution forecast** (dry-run the loop; show the exact claim order and terminal skip set) labelled a forecast.

**D4 — Both layers, one predicate.** The host (`sprint-run` § 2) and the per-plan runner (`ptp-parcel-fast` entry check, `SKILL.md:46`) must apply the *same* satisfaction rule. Divergence produces a claim-then-skip orphan: the host claims under the relaxed rule, the subagent immediately `SKIP`s, leaving a `CLAIMED` plan that preflight then misclassifies as an orphan.

**D5 — One state machine, five mirrors.** Mirror the status + predicate into: `plan-lifecycle.md` (enum, lifecycle flow, `depends_on` definition `:35`, Claim Protocol `:72`, Deviations `#1`), the `base-context.md` shared prefix (`:31` lifecycle, `:63` claim rule → `-Sync` → every locked agent) + `base-context.template.md`, `pass-the-parcel/SKILL.md` (state table `:33-46`, eligibility `:203`, § Batch Runner), `sprint-run` (v1→2), `ptp-parcel-fast` (v1→2), `sprint-status` (`:28`, `:57`), `sprint-plan`, `parcel-sprint.agent.md` (`:145` + preview), `SPRINTS.template.md:45`, `template-plan.md:4`, `HOW-TO.md:67`.

**Out of Scope:**
- **Batch sprint wrap-up** — a separate, dependent parcel, T1-E3.04 (this one only makes the state resolvable).
- Auto-clearing Gate D, advancing a plan past `PHASE_9`, or auto-archiving.
- Relaxing the `touches` predicate, queue order, or worktree isolation.
- Retiring `CLAIMED` or re-splitting it into `CLAIMED` + `IN_PROGRESS`.
- Rewriting historical plans, archives, or logs (`.devops/archive/**`, `.devops/logs/agent-changelog.md`).
- Per-plan `@agent-wrap-up` behaviour (unchanged; it still archives on the Gate D verdict).

**Perimeter Notes:**
- **Prefix lock.** `base-context.md` is the canonical shared prefix; the agent copies are derived. Edit `base-context.md` + `base-context.template.md`, then `scripts/check-parcel-prefix.ps1 -Sync` re-inlines byte-for-byte into every `parcel*` / `ptp-*` agent. Run `check-parcel-prefix.ps1` and `check-utf8-agents.ps1` before any push.
- **CI hard gate.** Bump `machinery-version` `43 → 44` in `.devops/sync-manifest.yaml` **and** record the literal `machinery-version: 44` in `.devops/logs/version-history.md`, or `validate.yml` "Machinery version discipline" fails.
- **Composes with per-plan wrap-up.** Because satisfaction is a disjunction, a sprint that manually wraps some plans and batches the rest needs no special handling.
- **Transitional readers.** Any tool that branches on `claim_status` (`sprint-status`, `sprint-close`) must recognise the new value, or it will silently mis-report an executed plan as in-flight.
